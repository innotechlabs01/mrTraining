# BUILD9-A — Auditoría child tables sensibles

## Estado general
- Local DB: 127.0.0.1:5435/mr_training_migration
- Tablas auditadas del primer grupo: 9
- Con RLS protegida: 3 (`message_threads`, `running_sessions`, `support_tickets`)

## Estructura y propiedad
- `message_threads` → parent direct, columna `coach_id`.
- `messages` → FK `thread_id -> message_threads`.
- `support_tickets` → parent direct, columna `coach_id`.
- `ticket_messages` → FK `ticket_id -> support_tickets`.
- `coach_sessions` → parent direct (RLS protegida en lista; auditoría confirmada indirectamente por las hijas).
- `session_exercises` → FK `session_id -> coach_sessions`.
- `session_ai_adjustments` → FK `session_id -> coach_sessions`.
- `running_sessions` → por usuario (`user_id`), protegida.
- `running_gps_points` → FK `session_id -> running_sessions`.
- `running_workout_snapshots` → FK `assignment_id -> running_workout_assignments` y `session_id -> running_sessions`.

## Políticas actuales
- `message_threads`: aislada por `coach_id`.
- `messages`: sin RLS directo; su protección implícita depende del thread mediante FK, pero no de RLS verificada.
- `support_tickets`: aislada por `coach_id`.
- `ticket_messages`: sin RLS directo; su protección depende de `support_tickets`.
- `running_sessions`: aislada por `user_id`.
- `running_gps_points`, `running_workout_snapshots`: sin RLS directo; su protección depende de `running_sessions` y `running_workout_assignments`.
- `session_exercises`, `session_ai_adjustments`: sin RLS directo; su protección depende de `coach_sessions`.

## Riesgos identificados
1. Las tablas hijas pueden ser leídas directamente si algún path DB o rol evita el handler.
2. `messages` y `ticket_messages` carecen de políticas directas de RLS para INSERT, UPDATE y DELETE.
3. `running_gps_points` y `running_workout_snapshots` pueden revelar datos derivados sin filtrar ownership.
4. `session_exercises` y `session_ai_adjustments` se propagan por `coach_sessions`, pero no tienen control directo.
5. Para snapshots hay dos relaciones (`assignment` y `session`) y se debe definir cuál gobierna el acceso.

## Dependencias y observaciones
- Para evitar recursión RLS, los funnels deben usar joins a tablas padre ya protegidas (`message_threads`, `support_tickets`, `coach_sessions`, `running_sessions`, `running_workout_assignments`).
- Para snapshots, conviene una única condición de acceso basada en una relación válida:
  - atleta propietario del `session_id`.
  - coach propietario del `assignment_id`.
- Si una tabla no necesita aislamiento por su naturaleza, debe documentarse individualmente en Build9-B.
- No se ha creado migración alguna.
- No se ha aplicado ninguna política.
