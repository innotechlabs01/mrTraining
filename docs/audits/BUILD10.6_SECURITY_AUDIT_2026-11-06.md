## 4. Critical finding: silent coach-branch RLS tautology (24 tables)

### 4.1 Root cause

Migration `406_rls_remaining_tables.sql` defines athlete-owned tables with this predicate shape:

```sql
CREATE POLICY policy_<table>_select ON public.<table> FOR SELECT
USING (
  athlete_id = NULLIF(current_setting('app.current_user_id', true)::text, '')
  OR EXISTS (
    SELECT 1
    FROM coach_athlete_links cal
    WHERE cal.athlete_id = athlete_id
      AND cal.coach_id = NULLIF(current_setting('app.current_coach_id', true)::text, '')
      AND cal.status = 'active'
  )
);
```

Because the inner query has its own alias `cal`, the unqualified `athlete_id` resolves to `cal.athlete_id`, not the outer table's `athlete_id`. The effective predicate is therefore `cal.athlete_id = cal.athlete_id`, which is always true. Thus any coach with at least one active link can see/write rows for any athlete. `WITH CHECK` has the same defect, so writes are also leaked.

### 4.2 Reproduction (local, read-only semantics; rolled back)

```sql
-- app role
BEGIN;
SELECT set_config('app.current_user_id', '', true);
SELECT set_config('app.current_coach_id', 'coach-blk-9b66c120', true);

-- unlinked athlete row is visible
SELECT count(*) FROM challenge_attempts;  -- returns 1

-- unlinked write is accepted, then rolled back
INSERT INTO athlete_favorites (id, athlete_id, item_type, item_id)
VALUES ('audit-probe', 'attacker-unlinked-athlete', 'x', 'y'); -- INSERT 0 1
ROLLBACK;
```

The probe was rolled back; no persistent data was changed.

## 7. Remaining DB-direct routes and exceptions

### 7.1 Classification summary

- Handler groups already wrapped in per-request UoW `withTx`: analytics, coach, coach_settlement, commission_entry, event, membership, message, support, running reads.
- Repositories with `WithExecutor` but not consistently invoked at service/handler boundary remain (ally, coachfeed, commission, config, exercise, invite, message, plan, running, store, support, subscription, training program/workout) per Build10.3.
- Pool-only repositories (alert, ally_catalog, ally_operations, ally_payment_declaration, audit, blog, challenge, checkin, community, favorite, formmetrics, formrecording, gamification, health, import, leaderboard, notification, onboarding, product, routine, today, training/*, trainingai, user, videoanalytics, videoview, workout) do not establish RLS context and rely on application SQL filters.
- Some repositories intentionally self-manage transactions (ally, ally_payment_declaration, coach, coach_settlement, commission_entry, formmetrics, plan, running service, program/workout, store, workout, commission). These are **EXCEPTION JUSTIFIED** where they are atomic multi-write operations, provided they set tenant context internally where required.

### 7.2 Justified exceptions

| Exception class | Tables / paths | Justification |
|---|---|---|
| Global/public content | `community_*`, `blog_posts` (public reads), challenge library | Public data by design |
| Partner/marketplace global | `allies`, `ally_*`, `coach_ally_relationships` | Shared partner dimension; access gated by service relationship resolution |
| System/audit/backend | `financial_audit`, `financial_audit_events`, `schema_migrations`, outbox | Backend-owned; not request-tenant scoped |
| Unauthenticated/webhook paths | Clerk webhook ingestion | Handled separately with SVIX verification |
| Atomic multi-write operations | repositories with self-managed `sql.Tx` | Preserve atomicity; must set tenant context internally |
| Legacy/integration fixtures | test-only seed helpers | Should use super/admin URL only; build10.5 hardened |

### 7.3 Tracked residuals (not justified as final)

- Tenant-sensitive repository methods in Build10.3 deferred list (`ally`, `ally_catalog`, `ally_operations`, `ally_payment_declaration`, `commission`, `exercise`, `invite`, `store`, plus many pool-only domains) are not yet wrapped in per-request UoW and still depend on caller-supplied filters.
- `running_workout_assignments` app-role athlete reads are guarded by `410` either-or policy, but broader transaction propagation for all read paths remains partial per Build10.4.
- Build10.2B risk classification should be treated as static evidence until UoW/context integration tests are added for each tenant-sensitive path.
