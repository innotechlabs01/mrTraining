# BUILD9-B — Diseño y revisión SQL de políticas child sensibles

Estado: solo diseño/análisis. No se ha creado ni aplicado la migración 409.
QA: NOT READY.

## 1. Decisión general
Aplicar RLS directo a las seis tablas hijas sin RLS actual, pero solo con políticas derivadas de sus tablas padre protegidas:
- `messages` → `message_threads`
- `ticket_messages` → `support_tickets`
- `running_gps_points` → `running_sessions`
- `running_workout_snapshots` → `running_workout_assignments` + `running_sessions`
- `session_exercises` → `coach_sessions`
- `session_ai_adjustments` → `coach_sessions`

Las tres tablas padre ya tienen RLS por coach/usuario y no consultan a sus hijos; no hay recursión directa por este diseño.

## 2. Matriz individual

### messages
Cadena de propiedad: `messages.thread_id -> message_threads.id -> message_threads.coach_id`.
Owner efectivo: coach del thread.
Acceso:
- Coach propietario: SELECT, INSERT, UPDATE y DELETE.
- Sin contexto: ningún acceso.
- Athleta: ninguno en este modelo actual, porque `message_threads` solo tiene `coach_id`.
USING: `thread_id` existe en `message_threads` con `coach_id = current app current_coach_id`.
WITH CHECK: igual, bloqueando cambios a un `thread_id` de otro coach.
Protección de FK: con `WITH CHECK` no puede reasignar el thread.
Recursión: no. La padre solo usa `coach_id`.

### ticket_messages
Cadena: `ticket_messages.ticket_id -> support_tickets.id -> support_tickets.coach_id`.
Owner efectivo: coach del ticket.
Política similar a messages.
Riesgo: si soporte se extiende a tickets creados por atletas, habrá que añadir acceso compartido; actualmente no está en el esquema.

### running_gps_points
Cadena: `running_gps_points.session_id -> running_sessions.id -> running_sessions.user_id`.
Owner efectivo: atleta propietario de la sesión.
Acceso:
- Solo el atleta dueño accede.
- Sin contexto: deny.
- Eliminación permitida solo al dueño; edición limitada.
- Coach no obtiene acceso directo a través de este path; la capa coach consume agregados o el propio atleta.

### running_workout_snapshots
Cadenas:
- snapshot.assignment_id -> running_workout_assignments.id -> assignment.coach_id
- snapshot.session_id -> running_sessions.id -> session.user_id

Modelo:
- Lectura para coach: assignment es suyo.
- Lectura para atleta: sesión es suya.
- Insert: debe validar que la assignment sea del coach contextual y la sesión sea del usuario contextual. Esto obliga a tener ambas condiciones y evita apropiación.
- No se permite UPDATE ni DELETE por esta migración; defaults de deny.
- No UPDATE/DELETE policy; privilegios de update/delete denegados por ausencia.

### session_exercises
Cadena: `session_exercises.session_id -> coach_sessions.id -> coach_sessions.coach_id`.
Owner efectivo: coach.
Política completa SELECT/INSERT/UPDATE/DELETE por coach.

### session_ai_adjustments
Cadena: `session_ai_adjustments.session_id -> coach_sessions.id -> coach_sessions.coach_id`.
Owner efectivo: coach.
Política completa SELECT/INSERT/UPDATE/DELETE por coach.
`applied` o `dismissed` son solo flags del coach propietario.

## 4. Riesgos y decisiones
- `messages` dependen de un thread perteneciente al coach contextual. Si el diseño de mensajería soporta participación de atletas, falta una tabla/relación adicional; no conviene abrir acceso aquí sin definir el modelo.
- `ticket_messages` depende de un ticket del coach. Igual observación.
- Para `running_workout_snapshots`, la lectura permitida por OR entre coach y atleta; la escritura requiere AND. Esto protege contra mover enlaces.
- RLScross-tables no presentan recursión porque padres no leen hijos.
- No se incluye `SECURITY DEFINER`.
- No se aplicará el SQL hasta autorización expresa.
- No se considera suficiente con tablas que tienen RLS habilitado; hace falta Build9-D con pruebas CRUD.

## 5. Recomendación para Build9-C
Autorizable con revisiones menores si se apruebe la semántica coach-only para messages/tickets; snapshot dual compromise necesita datos de prueba adicionales. No se ha creado archivo 409.
