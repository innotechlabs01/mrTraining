## 1. Testing Philosophy

### 1.1 Core Principles

**Every feature has tests.** No feature is complete without tests. Tests are not optional. They are not "nice to have." They are part of the feature definition. A PR without tests is an incomplete PR.

**Test behavior, not implementation.** Tests should verify what the code does, not how it does it. Changing the implementation (refactoring) should not break tests if the external behavior remains the same. This means testing through public APIs — component render output, API responses, domain entity methods — not internal state, private methods, or intermediate values.

**Tests are documentation.** A well-written test describes the expected behavior of the system. A new engineer should be able to read the test suite and understand what each component does, what edge cases it handles, and what errors it produces. Test names should read like sentences: "returns error when athlete ID is invalid" is better than "test_invalid_athlete_id."

**Fast feedback.** Unit tests run in milliseconds. Integration tests run in seconds. E2E tests run in minutes. The testing pyramid reflects this — many fast unit tests, fewer slower integration tests, fewest E2E tests.

**Reliable tests.** A test that fails intermittently (a "flaky" test) is worse than no test. It erodes trust in the test suite. Flaky tests are treated as bugs and fixed with the same priority as production bugs.

### 1.2 Coverage Targets

| Layer | Coverage Target | Measurement |
|-------|----------------|------------|
| Domain logic (entities, value objects, domain services) | 90%+ | Line coverage |
| Use cases / command handlers | 85%+ | Line coverage |
| Repository implementations | 80%+ | Line coverage |
| API handlers | 80%+ | Line coverage |
| Frontend components | 80%+ | Branch coverage |
| Critical user flows (E2E) | 100% | Flow coverage |
| Overall project | 85%+ | Line coverage |

Coverage is measured but not worshiped. 100% coverage of trivial getters and setters is meaningless. 80% coverage that tests every edge case is far more valuable than 95% coverage that tests only the happy path.

### 1.3 What NOT to Test

- **Trivial code**: Simple getters/setters, data class constructors, constants. Tested indirectly.
- **Framework internals**: Don't test that React renders JSX or that Next.js routes requests. Trust the framework.
- **Third-party library behavior**: Don't test that PostgreSQL stores data or that Paddle processes payments. Test your integration with the library.
- **Generated code**: Code generated by protobuf, freezed, json_serializable. Tested indirectly.
- **Visual appearance**: Don't test exact pixel positions. Test component structure — not CSS values.

## 2. Testing Pyramid

```
                    +-----------+
                    |    E2E    |  ~50 tests    (Playwright, integration_test)
                    |  (Flows)  |
                    +-----+-----+
                    +-----+-----+
                    |Integration|  ~500 tests   (Vitest + Test DB, Go httptest)
                    |  (APIs)   |
                    +-----+-----+
              +------+-----------+------+
              |      Unit Tests         |  ~2000+ tests (Vitest, go test, flutter test)
              | (Domain, Components)    |
              +-------------------------+
```

### 2.1 Test Distribution by Layer

**Unit Tests (70%):**
- Domain entities and value objects
- Domain services (pure business logic)
- Use cases (with mocked dependencies)
- React components (rendering, user interactions)
- Utility functions, formatters, validators
- Flutter widgets (rendering, interactions)

**Integration Tests (20%):**
- API endpoint behavior (full request-response cycle with real database)
- Repository implementations (real database queries)
- TanStack Query hooks (with MSW-mocked API)
- Middleware chain (authentication, authorization, rate limiting)
- Event handling and publishing
- Database migrations (up and down)

**E2E Tests (10%):**
- Critical user flows (sign up -> onboarding -> first workout)
- Payment flows (subscription purchase, upgrade, downgrade)
- Coach workflows (create program -> assign athlete -> review workout)
- Athlete workflows (view workout -> log sets -> complete session)
- Multi-tenant isolation (coach A cannot see coach B's athletes)
- Error paths (network failure, session expiry, rate limiting)

## 3. Unit Testing

### 3.1 Test Structure

Every test follows Arrange-Act-Assert:

```
// Arrange: set up test data, create dependencies, configure mocks
// Act: execute the behavior under test
// Assert: verify the outcome
```

Tests are organized by scenario, not by method:

```
describe('Workout.Complete()')
  |- when all exercise results are valid
  |   '-' transitions status to completed and raises WorkoutCompletedEvent
  |- when workout is already completed
  |   '-' returns ErrWorkoutAlreadyCompleted
  |- when RPE is out of range
  |   '-' returns ErrInvalidRPE
  '-' when exercise results reference unknown exercises
      '-' returns ErrInvalidExerciseResult
```

### 3.2 Mocking Philosophy

- Mock at the architectural boundary. Mock database calls, HTTP clients, event buses, and external services. Do not mock domain entities or value objects — they are plain data.
- Prefer fakes over mocks for complex dependencies. A fake in-memory repository is more maintainable than a mock that asserts specific method calls.
- Use test fixtures for complex input data. Factory functions produce valid test data with sensible defaults.
- Tests should not know about internal implementation. If a test verifies that a specific internal method was called with specific arguments, it tests implementation, not behavior.

### 3.3 Test Fixtures and Factories

```typescript
// test/fixtures/workout.fixture.ts
export function createWorkout(overrides: Partial<Workout> = {}): Workout {
  return {
    id: randomUUID(),
    athleteId: randomUUID(),

    sportType: 'gym',
    scheduledDate: new Date(),
    status: 'scheduled',
    exercises: [createWorkoutExercise()],
    ...overrides,
  };
}
```

```go
// internal/training/testing/fixtures.go
func CreateTestWorkout(t *testing.T, overrides ...func(*domain.Workout)) *domain.Workout {
    w := domain.NewWorkout(
        uuid.New(), uuid.New(), uuid.New(),
        "Test Workout", "gym",
        time.Now(),
    )
    for _, fn := range overrides {
        fn(w)
    }
    return w
}
```

## 4. Integration Testing

### 4.1 API Integration Tests (Go)

API integration tests verify the full request-response cycle with a real database:

```go
func TestCreateProgram_Success(t *testing.T) {
    db := testhelpers.NewTestDB(t)
    handler := training.NewHandler(/* dependencies */)
    app := setupTestApp(handler)

    req := httptest.NewRequest("POST", "/api/v1/training/programs", jsonBody(map[string]string{
        "name": "Test Program", "sport_type": "gym",
        "start_date": "2026-01-01", "end_date": "2026-03-01",
    }))
    req.Header.Set("Authorization", "Bearer "+testToken)
    req.Header.Set("X-Organization-ID", testOrgID)

    resp, _ := app.Test(req)

    assert.Equal(t, 201, resp.StatusCode)
}
```

Test Database Strategy:
- Each test package gets a fresh test database (created from migrations)
- Tests run in parallel with separate databases or schemas
- Test data cleaned up after each test
- Migrations run once per test package, not per test

### 4.2 Frontend Integration Tests (TypeScript)

Frontend integration tests verify components work correctly with real API data using MSW:

```typescript
import { http, HttpResponse } from 'msw';
import { setupServer } from 'msw/node';

const server = setupServer(

test('displays list of programs', async () => {

test('shows empty state when no programs', async () => {
  server.use(http.get('/api/v1/training/programs', () => {
    return HttpResponse.json({ data: [], pagination: { totalItems: 0 } });

  render(<ProgramListPage />);
  expect(await screen.findByText('No programs')).toBeInTheDocument();
});
```

### 4.3 Database Migration Tests

```go
func TestMigration_RoundTrip(t *testing.T) {
    db := testhelpers.NewTestDB(t)

    require.NoError(t, migrate.Up(db, 1))
    var exists bool
    db.QueryRow("SELECT EXISTS (SELECT FROM information_schema.tables WHERE table_name = 'organizations')").Scan(&exists)
    assert.True(t, exists)

    require.NoError(t, migrate.Down(db, 0))
    db.QueryRow("SELECT EXISTS (SELECT FROM information_schema.tables WHERE table_name = 'organizations')").Scan(&exists)
    assert.False(t, exists)
}
```

## 5. End-to-End Testing

### 5.1 E2E Flow Selection

E2E tests cover critical paths selected by:
- Business criticality: Can the company still make money if this flow is broken?
- User criticality: Can athletes still train and coaches still coach?
- Integration risk: Does this flow cross multiple system boundaries?
- Frequency: How often is this flow executed by real users?

### 5.2 Playwright (Web)

```typescript
test.describe('Coach Workflow', () => {
  test('create program, assign athlete, review workout', async ({ page }) => {
    await page.goto('/login');
    await page.fill('[name="email"]', 'coach@test.com');
    await page.fill('[name="password"]', 'test-password');
    await page.click('button[type="submit"]');
    await expect(page).toHaveURL('/training/programs');

    await page.click('text=New Program');
    await page.fill('[name="name"]', 'E2E Test Program');
    await page.selectOption('[name="sport_type"]', 'gym');
    await page.click('text=Create Program');
    await expect(page.locator('text=E2E Test Program')).toBeVisible();
  });
});
```

### 5.3 Flutter Integration Tests

```dart
void main() {
  IntegrationTestWidgetsFlutterBinding.ensureInitialized();

  testWidgets('athlete completes a workout', (tester) async {
    await tester.pumpWidget(const MrtrainingApp());
    await tester.pumpAndSettle();

    await tester.enterText(find.byKey(const Key('emailField')), 'athlete@test.com');
    await tester.enterText(find.byKey(const Key('passwordField')), 'test-password');
    await tester.tap(find.byKey(const Key('loginButton')));
    await tester.pumpAndSettle();

    expect(find.text("Today's Workout"), findsOneWidget);
  });
}
```

### 5.4 E2E Environment

- Tests run against a full staging environment (not production)
- Test data is seeded before the test suite runs
- Tests are isolated: each test creates its own data or uses a unique prefix
- Tests run in CI on every PR that changes frontend or API code
- Flaky tests (3 consecutive failures) are quarantined and must be fixed before release
- E2E test suite runtime target: < 15 minutes (parallelized)

## 6. Accessibility Testing

### 6.1 Automated Checks

- axe-core integrated into Playwright tests:

```typescript
import { injectAxe, checkA11y } from 'axe-playwright';

test('has no accessibility violations', async ({ page }) => {
  await page.goto('/training/programs');
  await injectAxe(page);
  await checkA11y(page, null, {
    detailedReport: true,
    detailedReportOptions: { html: true },
  });
});
```

- Every new component must pass axe-core checks
- Pre-existing violations tracked and must trend toward zero
- Critical/serious violations block the PR

### 6.2 Manual Checks

- Keyboard navigation: every interactive element reachable via keyboard alone
- Screen reader testing: VoiceOver (macOS), NVDA (Windows) for critical flows
- Focus management: focus visible at all times, focus order matches visual order
- Color contrast: WCAG AA minimum (4.5:1 normal text, 3:1 large text)
- Reduced motion: respect `prefers-reduced-motion`

## 7. Performance Testing

### 7.1 API Load Testing

- Tool: k6 (Grafana)
- Scenarios:
  - Sustained load: 1,000 concurrent users for 30 minutes
  - Spike testing: ramp from 100 to 2,000 users in 2 minutes
  - Stress testing: increase load until failure
  - Endurance testing: 500 concurrent users for 4 hours
- Targets:
  - P95 latency < 200ms under normal load
  - Error rate < 0.5% under normal load
  - No service crashes or OOM events under stress

### 7.2 Frontend Performance

- Lighthouse CI runs on every PR changing frontend code
- Performance budgets:
  - LCP < 2.5s
  - FID < 100ms
  - CLS < 0.1
  - JS bundle < 200KB (gzipped) initial page load
- Bundle size monitoring: PR comments show changes per route

### 7.3 Database Performance

- Query performance tested with EXPLAIN ANALYZE on representative data
- Slow query log monitored; queries > 100ms flagged for optimization
- Index usage verified: unused indexes removed, missing indexes created

## 8. Go Testing Standards

### 8.1 Test Organization

- Test files: `*_test.go` colocated with source files
- Table-driven tests for multiple inputs:

```go
func TestNewWorkout_Validation(t *testing.T) {
    tests := []struct {
        name    string
        input   CreateWorkoutParams
        wantErr error
    }{
        {"valid workout", validParams, nil},
        {"empty name", emptyNameParams, ErrInvalidName},
        {"invalid sport", invalidSportParams, ErrInvalidSportType},
    }
    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            _, err := domain.NewWorkout(tt.input)
            if tt.wantErr != nil {
                require.ErrorIs(t, err, tt.wantErr)
            } else {
                require.NoError(t, err)
            }
        })
    }
}
```

### 8.2 Test Helpers

- `testhelpers.NewTestDB(t)` — creates a fresh test database
- `testhelpers.SetupTestServer(t, handler)` — creates a test HTTP server
- `testhelpers.CreateTestUser(t, db, role)` — creates a test user with role
- `testhelpers.AssertAuditLog(t, db, action, entityType)` — verifies audit trail

### 8.3 Libraries

| Purpose | Library |
|---------|---------|
| Assertions | testify (assert + require) |
| HTTP testing | httptest (standard library) |
| Database testing | pgx pool with test database |
| Mocking | testify/mock or manual fakes |
| Race detection | `go test -race` |

## 9. TypeScript Testing Standards

### 9.1 Test Organization

- Test files: `*.test.ts` or `*.test.tsx` colocated with source files
- Test naming convention: `describe('ComponentName')` > `describe('method/prop/state')` > `it('what it should do')`

### 9.2 Component Testing

```typescript
import { render, screen, fireEvent } from '@testing-library/react';
import { ProgramCard } from './ProgramCard';

describe('ProgramCard', () => {
  it('displays program name and status', () => {
    render(<ProgramCard program={createTestProgram({ name: 'My Program' })} />);
    expect(screen.getByText('My Program')).toBeInTheDocument();
    expect(screen.getByText('draft')).toBeInTheDocument();
  });

  it('calls onSelect when clicked', () => {
    const onSelect = vi.fn();
    render(<ProgramCard program={createTestProgram()} onSelect={onSelect} />);
    fireEvent.click(screen.getByRole('button'));
    expect(onSelect).toHaveBeenCalledTimes(1);
  });

  it('shows athlete count when assigned', () => {
    render(<ProgramCard program={createTestProgram({ athleteCount: 5 })} />);
    expect(screen.getByText('5 athletes')).toBeInTheDocument();
  });
});
```

### 9.3 Hook Testing

```typescript
import { renderHook, waitFor } from '@testing-library/react';
import { QueryClient, QueryClientProvider } from '@tanstack/react-query';

function createWrapper() {
  const queryClient = new QueryClient({ defaultOptions: { queries: { retry: false } } });
  return ({ children }: { children: React.ReactNode }) => (
    <QueryClientProvider client={queryClient}>{children}</QueryClientProvider>
  );
}

test('usePrograms returns programs from API', async () => {
  const { result } = renderHook(
    () => usePrograms({ orgId: 'test-org' }),
    { wrapper: createWrapper() }
  );

  await waitFor(() => expect(result.current.isSuccess).toBe(true));
  expect(result.current.data).toHaveLength(2);
});
```

## 10. Flutter Testing Standards

### 10.1 Unit Tests (Domain Layer)

```dart
void main() {
  group('Workout.complete', () {
    test('transitions status to completed when all exercises are logged', () {
      final workout = Workout(
        id: 'test-id',
        athleteId: 'athlete-id',
        status: 'scheduled',
        exercises: [createTestExercise()],
        scheduledDate: DateTime.now(),
      );

      final result = workout.complete(
        rpe: 8,
        notes: 'Great session',
        exerciseResults: [createTestExerciseResult()],
      );

      expect(result.isRight(), true);
      expect(workout.status, 'completed');
      expect(workout.rpe, 8);
    });

    test('returns error when workout is already completed', () {
      final workout = createCompletedWorkout();
      final result = workout.complete(rpe: 8, notes: '', exerciseResults: []);
      expect(result.isLeft(), true);
    });
  });
}
```

## 11. CI Integration

### 11.1 CI Pipeline Stages

```
PR Opened
  |
  v
Lint & Typecheck (all languages)
  |
  v
Unit Tests (Go, TypeScript, Dart)
  |
  v
Integration Tests (Go with test DB, TypeScript with MSW)
  |
  v
Build (Docker images)
  |
  v
E2E Tests (Playwright, Flutter integration_test against staging)
  |
  v
PR Approved -> Merge
```

### 11.2 CI Requirements

- All tests must pass before merge
- Coverage must not decrease below project thresholds
- No new lint violations
- E2E test suite must complete without failures

### 11.3 Test Running Commands

```bash
# Frontend
pnpm test                  # Unit + integration tests (Vitest)
pnpm test:e2e              # E2E tests (Playwright)
pnpm test:coverage         # With coverage report

# Backend
go test ./...              # All tests
go test -race ./...        # Race detection
go test -coverprofile=coverage.out ./...  # Coverage

# Mobile
flutter test               # Unit + widget tests
flutter test --coverage    # With coverage
flutter test integration_test  # Integration tests
```

### 11.4 Coverage Reporting

- Coverage reports uploaded as CI artifacts
- Coverage trend tracked in dashboard (Codecov or custom)
- PR comments include coverage delta (+/- percentages)
- Coverage gates: merge blocked if coverage decreases > 2% below threshold
